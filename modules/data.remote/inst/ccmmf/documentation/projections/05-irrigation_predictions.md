# Irrigation Projections

## Overview

This section is split into two scripts. `caladapt_climate.R` turns downloaded Cal-Adapt NetCDFs into a
county daily climate lookup, and `irrigation_projection.R` runs the projection on that series using
the projected crop and date products.

The water balance is the same as the inventory, but everything going into it changes.
Weather comes from downscaled climate projections rather than observations, planting and harvest dates
come from the date projections, and peak greenness that the inventory observes has to be
reconstructed.

For simplicity, the prediction outputs are specific to GCM CESM2/ssp370, and the inventory resolves
precipitation and ET to the parcel level, while the projection averages 45 km Cal-Adapt grid cells to
one daily series per county. Parcel-level variation survives in crop type, soil water holding capacity,
rooting depth, and phenology, but not in the weather.

## Caladapt_climate.R

Overall, this script reads two types of files, each generated by an earlier workflow and whose locations need to be specified in the `config.yml`:

a. Cal-Adapt WRF NetCDFs, one per grid cell per year, named `<GCM>.<SSP>.<year>.nc`. Cells sit in
directories named by their grid position (`x47_y52`), and the current download covers California at
45 km, which comes to 198 cells.
b. California county boundaries, pulled from `tigris`

Assigning cells to counties: each grid cell directory holds a latitude and longitude for its centre,
which are turned into points and intersected with county polygons. At 45 km a small county can contain
no cell centre at all, so any county without one is assigned its nearest cell by projected distance.
Every county therefore ends up with at least one. The lookup is written out alongside the climate file.

Calculating reference ET: the hourly NetCDF variables — air temperature, wind speed, specific humidity,
pressure, shortwave and longwave radiation, precipitation — are aggregated to daily, then daily ET0 is
computed with the FAO-56 Penman-Monteith method. This is the same algorithm CIMIS uses, so the
projected ET0 is on the same footing as the inventory's observed values.

County aggregation: daily ET0 and precipitation are averaged across the cells assigned to each county,
giving one series per county per day. Large counties average several cells; small ones are represented
by a single cell, sometimes one whose centre falls outside the county.

**Important:** the year range has to extend one year past the final projection year. A crop planted
late in 2045 is harvested in 2046, and the water balance runs to the harvest date.

Processing is parallel across files, which is the slow part of this script. The output is a single CSV
of county daily climate.

## Irrigation_projection.R

Overall, this script reads six types of files to create the irrigation predictions:

a. Projected crop identity files, one per scenario and year
b. Projected planting and harvest files
c. `assigned_year=<year>_gapfilled.parquet` from the matched directory, for historical peak positions
d. The county daily climate file from `caladapt_climate.R`
e. SSURGO weights and soil tables
f. Crop water parameters from PEcAn's data.land module

Assembling crop cycles: projected crops join to their planting dates on crop code. Harvest carries no
crop code, so cycles are matched chronologically — both tables are sorted by their own date column and
paired by position within each parcel-year. A count mismatch between the two is a hard stop.

Reconstructing peak greenness: the water balance needs a peak date to shape the canopy curve, and
nothing observes one in the future. Instead the inventory phenology record gives where the peak fell as
a fraction of the season — the gap from onset to peak over the gap from onset to end — and that
fraction is applied to the projected season length. Matching previous scripts, this has five fallback levels:
1. county + crop code
2. county + crop class
3. crop code
4. crop class
5. statewide

Crop water parameters: each crop maps to a BISM crop name, which supplies the crop coefficient curve,
the management allowable depletion fraction, and the rooting depth. Where LandIQ codes have no exact
BISM match a small proxy table assigns the nearest reasonable crop. Parcels with no mapping, no rooting
depth, or no depletion fraction are dropped, and the counts by reason are printed.

Soil water holding capacity: effective capacity is computed per parcel and rooting depth from SSURGO
horizons, weighted across components and map units. Results are cached per county, so the first run
pays the cost and later runs reuse it. Rice is exempt, since the flooded model does not use a bucket
capacity.

Running the balance: counties run in parallel with 6 workers, with the largest ones first. Within a county, parcels sharing a crop,
planting date, peak date, and harvest date are grouped so the ET series is computed once for the group, slightly improving run time.
Each county writes its own file on completion, so an interrupted run resumes by skipping counties that
already have output.

**Important: simplifications**

1. Daily weather is uniform within a county, and comes from 45 km cells. This is the main trade off for reasonable run/computational times.

2. The canopy curve is piecewise linear — 0.15 at planting, rising to 1 at peak, falling back toward
0.15 at harvest.

3. Peak greenness is derived rather than observed, from where the peak historically fell within the
season for that crop and county.

4. Unclassified fallow and idle land receive no irrigation.

5. Parcels with no usable crop water parameters or no SSURGO capacity are dropped rather than given a
fallback, so this product covers fewer parcels than the others.

6. County files under `_county_tmp` are reused on a rerun, so you can pick up where you left off on irrigation prediction without having to restart. 

Any change to crop cycles, dates, or soil inputs requires deleting them, or the run will mix old and new results.

7. The script stops rather than carrying on if a crop has no planting or harvest date, if a harvest does
not follow its planting, if a peak date is impossible, if a climate day is missing, or if an irrigation
amount in the output is not positive.

## Outputs

`caladapt_climate.R` writes to your indvidually defined `work_root`: 

`caladapt_county_daily_climate.csv` — County, date, GCM, SSP, ET0_mm, precip_mm, and daily temperatures
`caladapt_county_site_lookup.csv` — which grid cell supplies each county

`irrigation_projection.R` writes to scenario subdirectories under the irrigation output root, matching
the inventory structure/column names:

`<scenario>/irrigation_statewide_<2024-2045>.parquet` — event_type, parcel_id, date, amount_mm

Per-county intermediate files remain under `<scenario>/_county_tmp/` after a run and are what makes
resuming possible. They are not a deliverable.
